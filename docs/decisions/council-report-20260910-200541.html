Council Report — Authentication Approach

AI Recruiter Agent · counciled 2026-09-10 · 5 advisors + 5 peer reviews + chairman
The question Which authentication approach should the AI Recruiter Agent adopt for its Owner (recruiter) accounts? Solo-built React+Vite SPA / FastAPI / Supabase (Postgres + RLS). Backend currently uses the Supabase service-role key (bypasses RLS), no per-Owner scoping yet. Single-Owner MVP; schema already supports multi-recruiter. Hard constraint: genuine zero recurring cost. Handles candidate PII under EU AI Act (high-risk) + India DPDP. Options weighed: Supabase Auth, roll-your-own FastAPI JWT, Better Auth, Logto, Zitadel, SuperTokens, Clerk, WorkOS AuthKit, Auth0/Firebase, passkeys.
COUNCIL VERDICT

Recommendation: Supabase Auth — as the minimal option, not the maximal one

The owners table, the auth_user_id FK, and the RLS policies are already written for it, so the marginal cost over any bespoke scheme is near zero. Every alternative is strictly worse on at least one of cost (self-hosted = a second stateful service to operate), risk (roll-your-own = a PII-breach surface for a solo builder), lock-in (Clerk / Auth0 / Firebase), or fit (their JWTs don't match the auth.uid() RLS policies you already have).

But the council's real finding: the auth vendor was never the hard part. The hard part is the recruiter-account security posture the regulations demand, which no vendor gives you by default. So the decision is Supabase Auth plus a defined hardening checklist:

  • Email/password login → TOTP MFA required on the Owner account (free on Supabase Auth)
  • Backup codes stored + a second break-glass Owner account (solo account recovery has no path otherwise)
  • Turn RLS back on as defense-in-depth beneath the app-code owner_id checks — not instead of them
  • Owner auth events written to the existing audit_log (DPDP / AI Act accountability)
  • Point Supabase custom SMTP at the existing Brevo credentials — the built-in SMTP is rate-limited and not production-grade
  • A keep-alive cron so the free-tier project can't auto-pause login out from under you (~7-day idle pause — already been bitten by this)
  • Short-lived JWTs with refresh, revocable on device loss

Skip: organizations, SSO/SAML, roles, team invites — genuinely premature for one user, and re-addable for free when a paying multi-seat customer actually appears.

The one thing to do first: In the Supabase dashboard — Authentication → point custom SMTP at your existing Brevo credentials, then enable the Email provider and require MFA. That 15-minute step is what turns "Supabase Auth" from a default into a compliance-defensible one, and it's the piece every advisor skipped. The FastAPI JWKS dependency and React login form come right after — but they're worthless guarding a mailbox that can't send a password reset, or an account with single-factor login to regulated PII.

Where the council clashes

The Contrarian vs. everyone else on whether to adopt real auth at all now. Contrarian: one user, so multi-tenant auth is speculative complexity. The rest: the machinery is for the regulator and future-you, and real Supabase Auth costs ~nothing more than a bespoke cookie scheme because the schema is already built for it. Chairman sides with the majority — the Contrarian is right you shouldn't build multi-tenant machinery, wrong that this argues against Supabase Auth, which is the minimal option here.

Does "RLS is currently bypassed" count against Supabase Auth? Contrarian says yes. Reviewer 5 reframes it correctly: it's an argument to turn RLS back on as defense-in-depth, which makes Supabase Auth more valuable, not less.

Blind spots the peer review caught

  • The Expansionist's upside case rests on a factual error — Supabase's free tier does not include SAML SSO. "Enterprise roadmap already built for free" is wrong.
  • Free-tier auto-pause (~7 days idle) takes auth down with the DB — no advisor proposed a mitigation.
  • Solo-Owner account recovery is unaddressed — one human, one credential, no second admin, regulated PII.
  • MFA is close to a compliance obligation here, not a nice-to-have (EU AI Act security-of-processing + DPDP).
  • Audit logging of Owner logins / PII access — a DPDP + AI Act accountability expectation.
  • Production email deliverability — Supabase's built-in SMTP is rate-limited; needs Brevo regardless.
  • Token/session revocation + JWT refresh — not automatic.
  • The service-role key stays in the backend regardless of auth choice — that residual risk needs its own plan.
Full advisor responses
The Contrarian
Everyone will converge on Supabase Auth because it's the same vendor and RLS "just works." Here's the fatal flaw: RLS does nothing for you. Your backend uses the service-role key and bypasses RLS entirely; every endpoint filters by owner_id in Python. So Supabase Auth's single biggest advertised advantage — native JWT-to-RLS integration — is worth exactly zero in your architecture. Strip that away and Supabase Auth is just a hosted auth service from a company whose pause-happy free-tier behavior you've already been burned by. If Supabase pauses your project, your auth dies with your DB. Single point of failure, single vendor, already bitten. The deeper problem nobody's questioning: you're solving multi-tenant auth for a single-Owner MVP. You have one user. It's you. The schema-for-multi-recruiter-later thing is speculative complexity. The zero-cost, zero-burden, zero-lock-in answer for one recruiter is a single env-var credential or one hashed password in config, plus a session cookie. Argon2 + one row. No vendor, no JWKS, no Node sidecar, no OIDC. When you actually sign recruiter #2 — if ever — you'll know your real requirements and can adopt Logto or Zitadel then, funded by customers. Rolling your own "full" auth is the trap: password reset, email verification, rate limiting, revocation — that's where solo builders leak PII. Build the minimum lock for a door only you walk through. The compliance risk isn't your auth library. It's the service-role key in your app tier and app-code owner_id filters you might forget.
The First Principles Thinker
You're asking "which vendor" when the real question is: what is authentication protecting, and from whom, at a stage with one user? Authentication here does exactly two jobs right now: (1) keep the internet out of a recruiter's dashboard holding candidate PII; (2) stamp a verified owner_id onto every request so your app-code filtering has something trustworthy to filter by. There is no user management, team invites, role hierarchy, or password-reset support burden — the userbase is you. Every option selling "great DX for onboarding users," "1M MAU free," "org management" solves a problem you don't have and prices in risk you can't afford. The actual decision axis: what produces a trustworthy owner_id on a FastAPI request with zero new infrastructure and zero new attack surface? That kills half the list. Better Auth, Logto, Zitadel, SuperTokens self-hosted — a second runtime you patch and monitor; not zero-cost, unpaid on-call. Clerk, Auth0, WorkOS, Firebase — proprietary identity dependency for a compliance-sensitive product, to save an afternoon. You already run Supabase. It already issues JWTs. Your schema already has auth_user_id wired to auth.users. The owner_id problem is already solved in your data model — you just haven't turned the key. The honest question isn't "which auth" — it's "why would I add anything?" The multi-recruiter future is a red herring: whatever issues verifiable JWTs for one Owner issues them for fifty.
The Expansionist
Auth is not plumbing here. It's the schema of your future org chart, and picking it well converts "solo MVP" into "multi-tenant SaaS with an enterprise motion" for near-zero marginal work. The underrated move: Supabase Auth as the identity spine, with RLS as the tenancy boundary. RLS policies keyed on auth.jwt() ->> 'owner_id' give you database-enforced tenant isolation for free — the single most expensive thing to retrofit later, and the exact control an EU AI Act auditor or DPDP data-processing agreement wants to see. You get a compliance artifact ("PII isolation enforced at the storage layer, not just app code") that becomes a sales asset with your first agency buyer. Then it compounds. Supabase Auth ships organizations, SSO/SAML, MFA in the same free tier — your entire agency-tier roadmap already built. One recruiter becomes a 12-seat firm becomes an enterprise account demanding Okta SSO, and you never swap auth vendors. Passkeys layer on top as a security differentiator. The adjacency: once Owners have real JWTs, your tokenized candidate links become scoped, signed, revocable artifacts from the same system, and partner/ATS integrations get OAuth-client credentials from infrastructure you already run. A marketplace surface. Bet on the choice that makes the 50-person version boring to build: Supabase Auth. Rolling your own throws away every upside path to save a week you'll spend on RLS policies anyway. [Peer review note: the free-tier SSO/SAML/orgs claim is factually wrong — SAML is a paid Supabase add-on. This undercuts the compounding-upside argument.]
The Outsider
The word "free" is doing a lot of hiding here. None of these options charge money; all of them charge attention. Self-hosting Logto, Zitadel, or SuperTokens means you now run an internet-facing service that stores password hashes for a regulated product, and you patch it forever. That's not $0 — that's a second job. The only genuinely "free" options are ones where someone else runs the server: Supabase Auth or a hosted tier. "Roll your own auth" for a product under EU and India hiring-AI regulation, handling applicant personal data, built by one person with no security team: alarming. Full stop. If there's a breach, "I hand-rolled the token logic" is the sentence in the incident report that ends the company. Cross it off. The mismatch you're asking about is real but backwards. It looks like heavy machinery for one user — but the machinery isn't for the user, it's for the regulator and future-you. That's justified. What's not justified is evaluating ten options. You have a Supabase database with RLS already wired to expect Supabase Auth tokens. Option 1 is the only one that makes your existing code smaller (drop the service-role key and the manual "filter by user id in every endpoint," itself a data-leak risk every time you forget). Lock-in fear is overweighted. Auth data is a table of emails and password hashes; it's the most portable thing in your stack. Migrating later is a weekend, not a rewrite. Pick Supabase Auth. Add passkeys later. Spend the saved weeks on regulatory documentation — the actual hard part nobody on this list solves.
The Executor
Ship this week: Option 1 (Supabase Auth). Everything else is multi-week or adds deployment units you'll babysit. Deployment-unit count: - Supabase Auth: zero new units. Already running inside the Supabase project you deploy. No new service, DB, or backup story. - Roll-your-own: zero units but ~2 weeks of code — password reset tokens, email verification, rate limiting, revocation, lockout, Brevo templates, security tests. You'll get one subtly wrong. - Better Auth / SuperTokens self-host / Logto / Zitadel: +1 service minimum, and 3 of 4 also +1 Postgres database — stateful, needs backups, migrations, free-tier keep-alive cron. On Render free tier it cold-starts and sleeps. "Self-hosted open source auth" is really "operate a second stateful system." - Clerk / WorkOS: zero units, but your RLS policies reference auth.uid(). Using them means minting a Supabase-compatible JWT or abandoning RLS. Extra glue, plus a vendor you'd later pay. Supabase Auth is the only option where the JWT drops straight into the auth.uid() policies you already wrote. Monday: Supabase dashboard → Auth → Providers → enable Email. Add @supabase/supabase-js to React, login form calling signInWithPassword. In FastAPI, one dependency that fetches Supabase's JWKS, verifies the bearer token, extracts sub, looks up owners.auth_user_id, returns owner_id. Create your Owner row by hand. Flip the backend from service-role key to per-request JWT. Done in a day or two.
Peer review highlights
Strongest response: The Executor (4 of 5 reviewers) — the only one that both reframes the decision correctly (deployment-unit count / operational burden is the deciding axis) and gives a concrete implementation path. The Outsider was the other pick (1 of 5). Biggest blind spot: The Expansionist (4 of 5 reviewers) — its entire upside thesis rests on RLS-enforced isolation being "already true" (the backend bypasses RLS today) and on SSO/SAML/orgs being in the free tier (SAML is a paid add-on). One reviewer instead flagged the Contrarian's "one hashed password" as the biggest miss — it ignores that adopting real Supabase Auth is near-free given the existing schema. What all five advisors missed (consensus across reviewers): free-tier auto-pause taking auth down with the DB; solo-Owner account recovery; MFA as a compliance obligation for high-risk PII; audit-logging of Owner access; production email deliverability (Supabase's built-in SMTP is rate-limited); token/session revocation and JWT refresh; and that the service-role key remains a residual risk in the backend regardless of auth choice.
